The devil is in the details.

July 13, 2026
Tech Agent

好久没写文章，是因为在开发自己的产品。最近新的版本趋于稳定，这才腾出时间，写写东西。

我自认为是现在比较了解如何开发一个产品的那一小撮人——软件工程加算法的双重背景，见过足够多的系统，也踩过足够多的坑。但真正自己下场做的时候，还是被复杂系统结结实实地困住了。那种感觉很微妙：你以为自己懂，直到你必须为每一个边界条件负责。

Demo is cheap, show me your System.

Vibe Coding 的时代开启了全民创造的浪潮。今天任何一个人，花几分钟、几句自然语言，就能让模型吐出一个能跑的 Demo。这本该是件让人兴奋的事，但它同时把一个残酷的事实放大了：从“能跑的 Demo”到“能持续运行的 System”之间的鸿沟，从来没有像现在这么深。Demo 越廉价，System 越昂贵。

这篇文章想聊的，就是那道鸿沟里的东西——它们全都藏在细节里。而衡量你有没有真正跨过去的标尺，是 eval。

Harness 会越来越厚

模型越强，就越可能被放到复杂、开放、风险更高的任务里。想把它的能力充分释放出来，又不让它的行为失控，你就需要一套更可靠、更可控的厚 harness。

所以 harness 不是简单给模型打补丁的外挂组件，而是模型与复杂系统、与真实世界发生交互时的那层控制层。用户以为自己在为模型付费，实际上他真正体验到的、决定产品好坏的，绝大部分是这层控制层。

那为什么 harness 会越来越厚？

一方面，为了让模型做更多事情，就得给它接入更多工具、数据、系统和真实世界的接口。模型与外部世界的触点越多，harness 需要负责的能力编排就越复杂。

另一方面，为了让整个系统更可靠，就需要更精确地约束模型能看到什么、能调用哪些工具、能采取哪些行动，以及出现异常时如何兜底。模型的行动空间越大，harness 承担的权限控制、流程约束和结果校验也就越多。

这两股力量叠加起来，结论就很反直觉：模型能力越强，harness 往往不是越薄，而是越厚——它既要帮模型把事情做成，也要确保它以可控的方式把事情做成。

我们的产品里就有大量这样的细节。举个例子：我的系统是 Java 负责编排、Python 负责执行、中间用消息队列做契约。听起来很清晰，但真正把我困住的，是那些没有编译器帮你兜底的地方——命令和事件的枚举在两端各定义一份，改一处必须手动同步另一处，否则消息就静默地路由错、反序列化失败；一个长任务被用户中途取消，你得在流程里预埋一个又一个 checkpoint，保证它能干净地停下来，而不是留下一堆半截的状态；前端刷新时要从后端重建整个运行时快照，哪些消息该合并、哪些该排除，全是 case by case 的判断。

这些细节没有一个是“性感”的，它们不会出现在 Demo 里，却是 System 的全部。复杂度不会消失，它只会从模型里被挤出来，堆到 harness 上，堆到你手上。

开发成本正在从开发，转向测试

当写代码这件事本身变得廉价，成本并不会消失，它只是换了个地方待着——从“把代码写出来”，挪到了“确认这段代码是对的”。开发在变便宜，测试在变贵。

其实写代码从来都不是最贵的那一步。真正贵的，是判断它到底对不对。Dijkstra 很早就说过一句被引用到烂的话：“测试只能证明 bug 的存在，永远无法证明 bug 不存在。”（“Program testing can be used to show the presence of bugs, but never to show their absence."）软件工程里还有一条老经验：读代码比写代码更难——你写的时候脑子里有完整的上下文，读的时候却要从字里行间反推别人（或者模型）当时在想什么。在 AI 之前，这些成本被“人写得慢”这件事天然摊平了；写得慢，你就有充足的时间边写边理解。

AI 把这个平衡彻底打破了。模型可以在几秒钟里吐出几百行、几千行看起来完全合理的代码，但“看起来合理”和“真的正确”之间隔着一整个测试的鸿沟。而且它产出的速度越快，等着你去审、去验证的东西就堆得越高。你被迫从一个“作者”变成一个“审稿人”——而审稿，恰恰是那件读比写更难的事。

业界已经在反复说这件事。Addy Osmani 把它总结成 AI 辅助编程的“70% 问题”：模型能轻松帮你把一个功能做到 70%，但剩下最难啃的 30%——边界条件、集成、真实场景下的正确性——依然得靠人一点点验证和收尾，而这 30% 往往吃掉你绝大部分时间。Simon Willison 也一直强调同一件事：LLM 写出来的代码，责任始终在你身上，你必须有能力读懂它、验证它，不能因为它是 AI 写的就默认它对。换句话说，AI 没有省掉测试这道工序，它只是把这道工序的占比顶到了前所未有的高度。

这件事我自己感受特别深。开发 verla 到现在，我发现自己大部分时间早已不在“写代码”上，而是在跑一批又一批的作业、盯着 summary.csv 里一行行的通过率，逐个点开失败的 case 去看它到底错在哪。写一版改动可能只要十分钟，但要确认这版改动在几十个真实任务上没有变差、没有引入新的诡异行为，可能要花掉一整个下午。代码是廉价的，让我睡得着觉的那份“确认”才是昂贵的。

所以能力的分野也在悄悄换标尺：过去我们问“你能不能把它写出来”，现在越来越多地在问“你能不能判断它到底对不对，而且是可规模化、可重复地判断”。而这，正好就是 eval 要解决的问题——它是这个时代真正稀缺的那种能力，也顺理成章地成了下一章要谈的壁垒。

Harness 越来越厚，用户的抱怨会越来越多

写在最后

回过头看，最让我意外的，不是这件事难，而是它比我这样一个“自认为最懂难度的人”预期的还要难。这恰恰说明，从 Demo 到 System 的门槛，被整个行业系统性地低估了。

Vibe Coding 让创造变得廉价，但也正因如此，真正的分野不再是“你能不能做出来”，而是“你能不能持续地做好、并且证明你做好了”。

Demo is cheap. The system is hard. And the eval is in the details.
